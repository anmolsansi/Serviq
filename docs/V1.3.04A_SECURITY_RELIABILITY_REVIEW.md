## Security review

### Tenant ownership

PASS.

- Cleanup rows are tenant-owned.
- Lookup/replay requires both tenant ID and cleanup ID.
- Foreign-tenant replay fails closed before a storage action.
- Tenant/source/object/cleanup identifiers and object keys are generated by the server.
- No tenant-facing cleanup CRUD route is introduced.

### Object-key integrity

PASS.

Trusted recovery does not accept an arbitrary raw key as replay input. The durable row stores `source_id`, `object_id`, and the generated key. Reconciliation regenerates the architecture-owned typed raw key and compares it with the persisted key before deletion. A mismatch exhausts safely instead of acting on the stored text blindly.

### Authorization boundary

PASS.

The normal upload continues to require `knowledge.sources.manage` before durable cleanup state or storage I/O is created. Cleanup replay is an internal worker/platform operation and does not weaken the existing user/tenant permission model.

### Sensitive data and logs

PASS by design and integration assertion.

Safe cleanup logs contain bounded cleanup/tenant IDs, status, and attempt count. They do not log raw object keys, original filenames, document content, storage credentials, tokens, bucket names, or endpoints. Integration coverage asserts the complete generated key is absent from cleanup logs.

### Destructive-action safety

PASS.

- A `referenced` cleanup is terminal and reconciliation never deletes its object.
- Storage I/O occurs outside database transactions.
- Generic PUT errors are treated as ambiguous. The cleanup remains durable through a 15-minute grace period and metadata confirmation instead of assuming an immediate DELETE proves final absence.
- Key mismatch fails safe to `exhausted`.
- Foreign-tenant lookup performs no storage delete.

## Reliability review

### Cross-store invariant

PASS.

The cleanup intent commits before `ObjectStorage.put_object`. Therefore a raw-object PUT cannot begin unless PostgreSQL already knows the exact tenant/source/object identity and generated key.

On normal success, the `knowledge_sources` insert and cleanup `referenced` transition commit in one PostgreSQL transaction. There is no committed source without the referenced terminal transition and no referenced transition without the source insert from that transaction.

### Double failure

PASS by implementation and integration coverage.

When PUT success is confirmed but source persistence fails, Serviq attempts immediate cleanup. If the delete also fails, the request still fails and the cleanup remains `pending` with bounded retry. If PostgreSQL is also unavailable while arming that retry, the original pre-PUT `prepared` row remains discoverable at its stale-preparation deadline.

### Ambiguous PUT outcome

PASS with conservative behavior.

A generic object-storage exception is not assumed to mean the server rejected the write. Request-time DELETE is only an optimization. The durable `prepared` row remains until the 15-minute deadline, which is well beyond the adapter's 5-second connect and 30-second read timeouts. Reconciliation uses HEAD/exists confirmation. Unresolved absence/HEAD failure consumes the bounded observation budget and becomes `exhausted` instead of silently disappearing.

### Retry and idempotency

PASS.

The request-time delete does not consume the background budget. Reconciliation is bounded to three attempts with 30-second, 5-minute, and 30-minute progression. Claiming increments the attempt and advances the next deadline while holding a row lock, then releases the transaction before storage I/O. Deleting an already-absent object remains idempotent through the OPE-301 storage contract.

### Crash recovery

PASS.

A process can crash after cleanup preparation, after PUT, after claim, after DELETE, or before a final DB status update without losing the durable identity of unresolved work. Prepared/pending state and moved retry deadlines keep the item discoverable. Repeating DELETE after a lost success-status update is safe.

### Exhaustion and operator visibility

PASS.

Attempt count is schema-bounded to 0..3. Unresolved work transitions to `exhausted` rather than retrying forever. The repository exposes aggregate counts across prepared/pending/referenced/succeeded/exhausted without returning object keys. `exhausted` is the durable V1.3.04A DLQ-equivalent state for later V1.10.09 operations.

### Migration and rollback

PASS by contract, final integration evidence still required.

The schema change is additive. Downgrade refuses to drop the table if any `prepared`, `pending`, or `exhausted` obligation remains. Operators must resolve unresolved work before schema rollback. Rolling application logic back to OPE-303 would reintroduce the original orphan risk and therefore is not a routine recovery path.

## Compatibility review

PASS.

V1.3.04A does not change:

- upload route/path;
- JSON/multipart public request formats;
- successful response shape/status;
- storage-error envelope;
- failed-upload visibility through `GET /api/v1/knowledge-sources`;
- file type/size limits;
- raw object-key layout;
- tenant/RBAC rules;
- parsing, indexing, or retrieval scope.

The cleanup table is internal operational state.

## Cost and complexity review

PASS.

The ticket adds one small PostgreSQL table and internal reconciliation functions. It does not add a broker, new object-storage listing API, new storage service, telemetry SDK, or always-on worker deployment. This keeps V1.3.04A compatible with the repository's future V1.3.06 outbox design instead of prematurely duplicating it.
