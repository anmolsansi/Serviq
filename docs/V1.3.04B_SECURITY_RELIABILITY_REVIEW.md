# V1.3.04B Security and Reliability Review

## Scope

Cumulative review of OPE-309 / V1.3.04B after PR #185 merged the knowledge upload quota and abuse-control implementation. This review covers the merged implementation plus the closeout correction for the Ruff-only test formatting regression.

## Security invariants reviewed

- Trusted tenant and workforce-user IDs remain server-owned and are not accepted from multipart form fields.
- The per-user upload limiter is tenant + workforce-user keyed and fails closed when Valkey is unavailable or returns malformed state.
- Multipart request limiting occurs before `request.form()`, preventing rejected attempts from consuming multipart parsing or object PUT capacity.
- Source, byte, reservation, cleanup, and legacy-size reconciliation queries are tenant-scoped.
- Legacy object keys are parsed only through the generated `tenants/{tenant}/knowledge/{source}/raw/{object}` contract and must match trusted tenant/source identity before storage metadata I/O.
- Quota/rate rejection performs no raw-object PUT and creates no user-visible source row.
- Error responses contain only stable codes/messages plus bounded retry timing. They do not expose object keys, bucket credentials, raw filenames, file contents, tokens, or foreign-tenant usage.
- The existing `knowledge.sources.manage` permission boundary remains in force.

## Reliability invariants reviewed

- PostgreSQL, not Valkey, is authoritative for committed source count, committed file bytes, and durable upload reservations.
- Tenant-row locking serializes source/byte/concurrency admission across cooperating API workers and prevents quota oversubscription races.
- No object-storage HEAD/PUT/DELETE call is performed while the quota admission database transaction is open.
- Existing file rows with unknown size are reconciled through typed storage HEAD before new file bytes can be reserved. Unknown or contradictory usage fails closed before PUT.
- A reservation is created before raw PUT and bound to the V1.3.04A cleanup intent before PUT is permitted.
- Successful source persistence writes the exact validated byte count and releases the reservation atomically with cleanup transition to `referenced`.
- Confirmed request-time/background cleanup releases the reservation atomically with cleanup transition to `succeeded`.
- Linked `prepared`, `pending`, or `exhausted` cleanup obligations continue charging source/byte quota, so an ambiguous possible object cannot silently become free capacity.
- Handled failures best-effort expire active concurrency immediately. Crash-only concurrency over-blocking is bounded by the ten-minute lease.
- Expired unlinked reservations are reclaimable because V1.3.04A forbids valid raw PUT before cleanup-intent commit.
- Migration `20260828_0011` is additive and refuses downgrade while reservation rows exist.

## Test and CI evidence

Merged implementation evidence includes unit coverage for the Valkey Lua decision and malformed/failure behavior, canonical raw-key parsing tests, real PostgreSQL concurrent reservation and tenant-isolation tests, API-level zero-PUT rejection tests, real Valkey limit enforcement, real S3-compatible legacy byte reconciliation, migration upgrade/downgrade coverage, and the dedicated `Knowledge Quota Integration` workflow.

The first post-merge `main` quality run failed only because `test_knowledge_quota_postgres.py` contained one unused `UUID` import and two lines over the repository's Ruff line-length limit. Database integration, object-storage integration, the dedicated real-dependencies quota job, CodeQL, Gitleaks, Trivy, and dependency auditing were otherwise green on the merge commit. The closeout branch removes that unused import and wraps those expressions without changing behavior. Final completion requires the closeout PR's CI and Security checks to be green.

## Threat/failure cases explicitly considered

1. Repeated authorized upload attempts: bounded by the fail-closed per-user Valkey counter.
2. Concurrent workers racing remaining tenant capacity: serialized by tenant-row lock.
3. Cache restart/eviction: cannot erase durable byte/source accounting because Valkey does not own it.
4. API crash before cleanup intent: only an unlinked reservation remains and its concurrency/source/byte hold self-reclaims after the bounded lease.
5. API crash after cleanup intent / ambiguous PUT: linked reservation remains charged until cleanup/source outcome is established.
6. Legacy row without known bytes: storage metadata is established safely or new file admission fails closed.
7. Cross-tenant key substitution: rejected before storage I/O by canonical key/identity validation.
8. Operator temptation to clear exhausted reservations: runbook explicitly forbids clearing them merely to restore capacity without establishing object/source outcome.

## Residual risks and out-of-scope work

- These hard limits are not billing entitlements or paid-overage policy.
- There is no customer-facing quota-management API or platform override in this ticket.
- The worker remains an early foundation; the ticket provides durable cleanup/reconciliation contracts but does not claim a general scheduler or purge lifecycle is deployed.
- Production deployment, full load testing, SLO/alert ownership, and broader platform rate-policy surfacing remain later roadmap work.

## Review conclusion

No blocker was found in the V1.3.04B security or consistency model. The architecture preserves the V1.3.04A pre-PUT durability boundary, uses PostgreSQL for durable quota truth, limits Valkey to short-window request control, and fails closed when authoritative usage cannot be established. Completion is approved once the follow-up closeout PR proves repository quality and Security checks green and tracking is synchronized.
