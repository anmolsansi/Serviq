## 1. Why this ticket exists

Serviq is intended to be a reusable production customer-operations platform rather than a hard-coded chatbot demo. However, implementation tickets need one concrete reference domain so the first knowledge sources, synthetic records, tool contracts, policy rules, evaluation cases, and end-to-end scenarios can be built without every engineer inventing a different business model.

OPE-251 therefore freezes the first reference configuration before MAS-7 and downstream implementation begins.

## 2. Work performed

### 2.1 Reviewed the original candidate set

The initial candidate set was DoorDash, Shopify, Etsy, and Stripe. The review considered:

- how well public support/documentation content maps to real customer-support questions;
- whether the domain supports a read-only status tool, an eligibility/policy tool, and a protected mutation;
- whether private operational data can be represented synthetically;
- how clearly the resulting demo communicates Serviq's value to recruiters, engineering reviewers, and potential clients;
- source-access and ingestion risk;
- how well the domain can evolve into future real integrations.

### 2.2 Initially froze Stripe-only

The first OPE-251 decision selected Stripe public documentation plus a synthetic payment domain because Stripe has strong technical documentation and a clean tool story around payment status, refund eligibility, and refund creation.

That decision was recorded in `CCR-002-demo-domain-freeze.md` and intentionally did not execute real payments.

### 2.3 Revised the product decision to DoorDash + Stripe

The reference configuration was then strengthened to use two clearly separated business domains:

- DoorDash public support material supplies the customer-support/delivery knowledge context.
- Stripe public documentation supplies the payment/refund-provider context.
- Serviq-owned synthetic records supply all private customer, order, delivery, payment, refund, and support state.

The revised decision is recorded in `CCR-003-doordash-stripe-demo-composition.md`, which supersedes the Stripe-only product choice while preserving CCR-002 as historical decision context.

## 3. Why the combined model is better

A Stripe-only demo is technically valid, but it can look like a payment-support application rather than a general customer-operations platform.

The combined DoorDash + Stripe reference model gives Serviq a much richer workflow:

```text
Customer
  |
  +--> delivery/order question
  |       |
  |       +--> DoorDash public support knowledge
  |       +--> synthetic order/delivery state
  |
  +--> refund/payment question
          |
          +--> DoorDash resolution guidance
          +--> synthetic order/item state
          +--> Stripe payment/refund knowledge
          +--> Serviq policy + protected mutation
```

This improves the project in four ways:

1. **Broader product demonstration.** Serviq now demonstrates support, logistics, payments, policy, actions, and human handoff rather than only payment support.
2. **Cross-system orchestration.** The agent has to combine knowledge and state from distinct operational boundaries, which is much closer to enterprise support systems.
3. **Cleaner architecture proof.** The tool layer must remain provider-neutral and domain-oriented instead of leaking Stripe-specific types through the whole codebase.
4. **Stronger portfolio value.** A reviewer can see how the same platform could later be customized for food delivery, commerce, travel, SaaS, or other industries.

## 4. Important accuracy rule

Serviq must never state or imply that DoorDash uses Stripe internally.

The reference configuration means only:

> "Serviq uses DoorDash public support content as a delivery/customer-support domain and a Stripe-shaped synthetic payment adapter as a separate reference payment provider."

The two companies are used as public reference domains for a portfolio project; there is no claimed commercial relationship between them or with Serviq.

## 6. Synthetic data required

The reference implementation requires:

- `demo_customers` — synthetic tenant-scoped customer records;
- `demo_orders` — synthetic delivery orders;
- `demo_order_items` — item-level state used for missing/incorrect-item scenarios;
- `demo_deliveries` — synthetic fulfillment and delivery status;
- `demo_order_events` — deterministic order/delivery event history;
- `demo_payments` — synthetic Stripe-shaped payment state linked to orders;
- `demo_refund_rules` — configurable synthetic eligibility and approval rules;
- `demo_refunds` — idempotent protected refund records;
- `demo_support_cases` — human-escalation and resolution context.

No real DoorDash or Stripe PII, customer data, credentials, payment instruments, or transactions are needed.

## 7. Tool contracts frozen by this ticket

### `demo.get_delivery_order_status`

Read-only. Returns verified synthetic order and delivery state for a customer-scoped order.

**Why:** Order status is a deterministic business-data operation. Serviq should not waste an expensive generative call or hallucinate a delivery state that already exists in structured data.

**Improvement:** Demonstrates deterministic routing, customer authorization, normalized tool output, and low-latency support paths.

### `demo.check_order_resolution_eligibility`

Read-only. Evaluates the reported issue against synthetic order/item/delivery/payment state and Serviq policy inputs.

**Why:** Eligibility is more complex than either RAG or a raw database lookup. It combines operational state and policy without performing a mutation.

**Improvement:** Demonstrates how Serviq separates reasoning/evidence from authorization and execution.

### `demo.create_refund`

Protected mutation. Creates an idempotent synthetic refund only after policy, customer confirmation, and human approval requirements have been satisfied.

**Why:** A production AI support platform must prove that it can take useful actions without allowing the model to mutate business state directly.

**Improvement:** Demonstrates the complete governed action chain: identity -> policy -> confirmation/approval -> idempotent execution -> reconciliation -> audit.

## 8. Public-source policy

The repository will not store a wholesale copy of either company's documentation.

The implementation should instead maintain a Serviq-authored source manifest containing only approved URLs/provenance and topic metadata. Ingestion must obey the architecture's network and source-security rules. If a source disallows automated access or becomes inaccessible, Serviq disables that entry rather than bypassing controls.

This improves legal/operational hygiene and also makes the ingestion system itself part of the portfolio demonstration.

## 9. Demo scenarios unlocked

The decision now supports complete V1 scenarios such as:

- "Where is my order?"
- "My order says delivered but I didn't receive it."
- "One item is missing. What can I do?"
- "I received the wrong item."
- "Can I get a refund?"
- "Refund only the missing item."
- "Why is my refund still pending?"
- customer confirmation before a refund;
- human approval for high-value/policy-sensitive refunds;
- payment-provider failure/unknown-state reconciliation;
- human takeover without making the customer repeat the entire problem.

## 11. What this improves in Serviq

Before OPE-251, the architecture said Serviq would support real-company public documentation plus synthetic private data, but builders still had to decide what those words meant.

After OPE-251:

- the domain is concrete;
- the three required tool classes have stable names and responsibilities;
- synthetic record types are known;
- RAG evaluation topics can be written against a stable domain;
- policy and approval fixtures can use realistic refund scenarios;
- human-handoff payloads can include order, delivery, payment, and refund context;
- frontend demo flows have realistic customer stories;
- backend builders no longer invent domain behavior independently.
