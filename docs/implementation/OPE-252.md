## 1. What is this ticket about?

Before building screens, APIs, AI agents, databases, or integrations, Serviq needs a clean place for all of that code to live.

A useful analogy is building a school before students arrive.

You do not start by teaching chemistry in an empty field. First you create the building, label the classrooms, decide where the library goes, set rules for how rooms are organized, and make sure everyone knows which entrance to use.

OPE-252 creates that kind of foundation for the Serviq repository.

There is almost no customer-facing product in this ticket. Instead, we are creating the rules and files that make future development predictable.

---

## 2. What is a monorepo?

Serviq will eventually contain several applications and services.

For example:

```text
Client Console
Customer Support Website
Platform Operator Console
Backend API
AI Agent Runtime
Background Workers
Shared UI Components
Shared Data Contracts
```

We want these to live in one GitHub repository rather than scattering them across many unrelated repositories.

That approach is called a **monorepo**.

Think of a monorepo as one large school binder with labeled sections.

Instead of carrying ten separate notebooks and trying to remember which one contains what, everything is in one place but still organized clearly.

The planned structure looks roughly like this:

```text
Serviq/
  apps/
    client-console/
    customer-web/
    platform-console/

  packages/
    shared-code-will-go-here-later/

  services/
    backend-services-will-go-here-later/

  docs/
    product-and-engineering-documentation/
```

OPE-252 does not create all of those applications. It creates the root rules that allow them to be added correctly later.

## 3. What files did we create?

This ticket created five important files at the top level of the repository.

### 3.1 `package.json`

This is the main JavaScript/TypeScript project description file.

A simple analogy is the label on the outside of the binder.

It tells development tools things such as:

- this repository is a private workspace rather than something we publish directly as an npm library;
- which package manager we expect engineers to use;
- which common commands exist;
- where the JavaScript/TypeScript toolchain starts.

The root file intentionally does **not** contain application features.

It contains only shared project-level commands such as placeholders for:

```text
lint
check types
test
```

Why keep it small?

Because if we put application-specific dependencies at the root, every app would accidentally become coupled to the same dependency list. Keeping the root clean makes each application easier to understand and maintain.

---

### 3.2 `pnpm-workspace.yaml`

This file tells the package manager which folders are part of the JavaScript/TypeScript workspace.

In plain English, it says:

```text
Look inside apps/*
Look inside packages/*
Treat projects in those folders as members of the same workspace
```

It deliberately does not automatically include Python backend services.

Why?

Because JavaScript packages and Python services use different package-management systems. Mixing them would make the workspace confusing.

A school analogy would be: the student directory includes classrooms, but it does not pretend the cafeteria freezer is a classroom just because it is in the same building.

---

### 3.3 `.nvmrc`

Different versions of Node.js can behave differently.

Node.js is the runtime used by our Next.js frontend applications.

The `.nvmrc` file says which major Node version Serviq developers should use.

Why does this matter?

Imagine one student using Microsoft Word 2003 and another using a modern version. A document may work on one computer and break on another.

Pinning the Node version reduces "works on my machine" problems.

When a developer enters the repository, their environment can read this file and switch to the expected Node version.

---

### 3.4 `.gitignore`

Git is supposed to store source code and important project files. It should **not** store every temporary file created on a developer's computer.

`.gitignore` tells Git what not to upload.

Examples include:

```text
.env files with local secrets
node_modules dependency folders
build output
coverage reports
Python cache files
IDE settings
local object-storage data
operating-system junk files
```

This file is important for two major reasons.

#### Security

A developer may have an `.env` file containing something like:

```text
OPENAI_API_KEY=...
DATABASE_PASSWORD=...
```

We never want that accidentally committed to a public GitHub repository.

#### Repository cleanliness

Dependency folders can contain tens of thousands of generated files. They can always be recreated from package definitions, so storing them in Git would make the repository huge and noisy for no benefit.

---

### 3.5 `.editorconfig`

Different developers use different editors: VS Code, IntelliJ, Vim, Cursor, and others.

Without shared formatting rules, one person may save files with different indentation or line endings than another person.

`.editorconfig` defines basic formatting expectations such as:

- UTF-8 text;
- standard line endings;
- final newline at the end of files;
- two-space indentation for JavaScript/TypeScript/YAML;
- four-space indentation for Python.

This is not about making the code "prettier." It prevents useless Git changes where a file appears to have changed simply because an editor reformatted every line differently.

## 4. What does pnpm do?

`pnpm` is the package manager chosen for the JavaScript/TypeScript part of Serviq.

A package manager downloads and organizes the libraries our code depends on.

For example, when a Next.js application says it needs React, Next.js, TypeScript, and Tailwind, pnpm handles installing those dependencies.

Why use one package manager consistently?

If one engineer uses npm, another uses Yarn, and another uses pnpm, the dependency tree can be resolved differently and multiple lockfiles can appear.

By freezing one tool, we reduce that uncertainty.

## 5. What is the practical effect of this ticket?

Before OPE-252, someone starting a frontend ticket would have to make decisions such as:

```text
Where should the app live?
Which package manager should I use?
Which Node version?
Should I create a separate workspace file?
What should Git ignore?
What indentation rules should I use?
```

That is dangerous because five engineers might make five different decisions.

After OPE-252, those questions already have answers.

A future frontend engineer can simply create:

```text
apps/client-console
```

or:

```text
apps/customer-web
```

and the root workspace already knows where it belongs.

## 6. Why did we make several small commits instead of one huge commit?

This ticket was intentionally committed in small logical steps.

The major commits were:

```text
429c605 — add root package.json
79817b8 — add pnpm workspace definition
757be5b — lock Node version
A4a56b0 — add Git ignore/security rules
5973b39 — add editor configuration
```

Why does that help?

Imagine receiving a box containing five machine parts with no explanation. If the machine breaks, it is hard to know which part caused the problem.

Small commits are like installing one part at a time and writing down what it does.

They make it easier to:

- review changes;
- understand history;
- revert one bad decision without deleting unrelated work;
- find when a problem was introduced.

## 7. What does this improve?

### Developer consistency

Every engineer starts from the same workspace rules.

### Security

Secret-bearing local files are excluded from Git by default.

### Maintainability

Apps can remain independent while still sharing one repository.

### Faster onboarding

A new contributor does not have to guess how the project is organized.

### Future automation

CI pipelines will later be able to use predictable commands and paths.

### Lower risk of accidental architecture drift

The repository structure now follows the architecture documents rather than whichever folder names an individual developer prefers.

## 8. What did we intentionally NOT do?

This ticket is only the root foundation.

We did not:

- create the Client Console;
- create the Customer Web app;
- create the Platform Console;
- create backend Python services;
- create Docker Compose;
- add CI workflows;
- add databases;
- add AI libraries;
- add authentication;
- add product features.

Why not do everything at once?

Because a large "setup everything" ticket is difficult to review and debug.

We want each ticket to have one clear responsibility.

## 11. Plain-English glossary

**Repository / repo:** A folder tracked by Git and stored on GitHub.

**Monorepo:** One repository containing multiple related applications and packages.

**Node.js:** The JavaScript runtime used by our Next.js applications and build tools.

**pnpm:** The tool that installs and manages JavaScript/TypeScript dependencies.

**Workspace:** A group of related packages managed together.

**Dependency:** Reusable software our application relies on, such as React.

**Environment variable:** A configuration value supplied outside the code, often used for URLs, secrets, or API keys.

**`.env`:** A common local file containing environment variables. It must not be committed when it contains secrets.

**Lint:** Automated checks for code-quality and style problems.

**Typecheck:** A check that verifies values are being used with the correct expected data types.

**CI:** Automated tests/checks that GitHub runs when code is pushed or proposed for merging.
