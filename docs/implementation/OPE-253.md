## 1. What is the Client Console?

Serviq has different kinds of users.

One group is the business that buys or operates Serviq. These users are not the end customers asking for support. They are the people inside the company who manage the AI system.

For example, imagine Serviq is being used by a large delivery company. The company's internal team may want to:

- upload or connect support documentation;
- configure which AI models are used;
- set refund and approval rules;
- review customer conversations;
- take over conversations when the AI needs help;
- manage support agents and permissions;
- see analytics;
- inspect audit history;
- configure integrations.

The **Client Console** is the web application where those business users will eventually do all of that.

OPE-253 does not build those features yet. It creates the empty but working application shell they will live inside.

---

## 2. Why create an empty application first?

A common software mistake is trying to build the dashboard, login, analytics, settings, and business logic all at the same time.

That makes failures hard to diagnose.

We are using a layered approach instead.

Think of building a house:

```text
Foundation
   ↓
Frame
   ↓
Walls
   ↓
Electricity/plumbing
   ↓
Rooms and furniture
```

OPE-252 created the shared repository foundation.

OPE-253 creates the **frame of the Client Console**.

Later tickets will add the rooms and furniture.

---

## 3. Where does the application live?

The application is created at:

```text
apps/client-console/
```

Its package name is:

```text
@serviq/client-console
```

Why use a precise path and package name?

Because future scripts, CI jobs, shared packages, deployment configuration, and engineers need one stable name for the application.

If one ticket called it `admin`, another called it `dashboard`, and another called it `client-app`, the repository would quickly become confusing.

## 4. What technology did we use?

The Client Console uses the frontend stack already frozen in the Serviq architecture.

### Next.js

Next.js is the main web application framework.

A simple way to think about it is that React gives us the building blocks for screens and Next.js gives us the structure around those blocks: pages, routing, build process, server capabilities, and production packaging.

### React

React is the library used to build the visible user interface from reusable components.

For example, future Serviq screens may contain reusable pieces such as:

```text
Conversation Card
Knowledge Source Row
Escalation Badge
Approval Dialog
Analytics Chart
```

React makes that style of interface practical.

### TypeScript

TypeScript is JavaScript with stronger rules about what kind of data is allowed.

For a non-technical analogy, imagine a form that says:

```text
Age: must be a number
Email: must be text
Approved: must be yes/no
```

Without those rules, someone could accidentally put "hello" into the age field.

TypeScript catches many similar mistakes before the code reaches users.

We enabled **strict TypeScript** because Serviq will eventually handle permissions, customer data, tool actions, and financial-style workflows where silent data mistakes are dangerous.

### Tailwind CSS

Tailwind is used for styling the interface.

It helps developers create layouts, spacing, typography, responsive behavior, and visual states in a consistent way.

OPE-253 only wires Tailwind into the app. It does not build the final Serviq design system yet.

## 5. What files were added, and what does each one do?

The scaffold was intentionally committed in small pieces.

### `apps/client-console/package.json`

This file describes the Client Console package itself.

It declares the application's dependencies and commands such as:

```text
dev       → run the app locally
build     → create a production build
lint      → check code-quality rules
typecheck → verify TypeScript types
```

Why app-local commands?

Because we want to be able to validate this app independently from every other application in the repository.

---

### `tsconfig.json`

This configures TypeScript.

The important decision is strict checking.

This improves reliability because the compiler catches more invalid assumptions before runtime.

---

### `next.config.ts`

This is the Next.js configuration file.

At this stage it stays minimal.

Why minimal?

Because every custom configuration option becomes another thing future engineers must understand and maintain. We only add custom behavior when the product actually needs it.

---

### ESLint configuration

ESLint automatically checks the source code for common problems and bad patterns.

Think of it like spell-check for code, except it can catch things such as suspicious JavaScript patterns rather than spelling mistakes.

It cannot prove the application is correct, but it catches many preventable errors.

---

### PostCSS / Tailwind setup

These files connect Tailwind styling into the application build process.

Without this wiring, Tailwind classes written in the interface would not be converted into the CSS the browser understands.

---

### `src/app/globals.css`

This is the global stylesheet.

For now it contains only the minimal base styling needed by the scaffold.

We deliberately avoided pretending the full Serviq visual design exists before its design-system tickets are implemented.

---

### `src/app/layout.tsx`

This is the top-level layout of the application.

Every page inside the Client Console will eventually live inside this structure.

It is also where basic page metadata can be defined, such as the application title.

A simple analogy: if individual pages are rooms, the root layout is the building around them.

---

### `src/app/page.tsx`

This is the current home page.

It only shows a simple Serviq Client Console foundation message.

That small page has an important purpose: it proves that the app has a real route and a visible output without introducing fake business features.

## 6. What happens when a developer runs this app?

Once dependencies are installed, the intended local flow is:

```text
Developer runs the Client Console
        ↓
Next.js starts a local web server
        ↓
Browser requests the home page
        ↓
Next.js loads the root layout
        ↓
The Client Console page is rendered
        ↓
Tailwind/global styles are applied
        ↓
The browser displays the Serviq foundation page
```

At this stage there is no database call, no login, no AI request, and no customer data.

That simplicity is intentional.

---

## 7. Why is the Client Console separate from the customer-facing app?

The business console and the customer chat serve very different people.

A customer needs a simple experience such as:

```text
Ask question
See answer
Confirm action
Talk to human
```

A business administrator may need dense operational screens containing filters, tables, configuration, analytics, permissions, and audit data.

Mixing both into one application would make security and product design harder.

The separation also helps us enforce different authentication rules later.

The Client Console is for trusted workforce users. The Customer Web app is for external end customers.

## 9. What did we intentionally NOT add?

We did not add:

- authentication;
- navigation/sidebar;
- API calls;
- customer data;
- charts;
- dashboard widgets;
- AI configuration screens;
- conversation screens;
- support inbox;
- design-system components;
- fake loading data;
- backend logic.

Why is that good?

Because this ticket's job is application scaffolding, not feature development.

Keeping scope narrow makes review easier and prevents hidden architecture decisions from slipping into an unrelated setup ticket.

---

## 10. Why did we use micro-level commits?

The scaffold was broken into small commits for configuration, TypeScript, Next.js, linting, Tailwind, global CSS, layout, and the visible page.

That gives us a history similar to:

```text
Create package definition
      ↓
Configure TypeScript
      ↓
Configure Next.js
      ↓
Configure linting
      ↓
Wire styling pipeline
      ↓
Add global styles
      ↓
Add root layout
      ↓
Add visible foundation page
```

A reviewer can understand each logical change instead of opening one giant scaffold commit containing everything at once.

## 11. What does this improve?

### Reliability

Strict TypeScript and linting establish safety checks before real features are added.

### Maintainability

The Client Console has its own clearly owned application boundary.

### Security preparation

The future workforce trust boundary is separated from the public customer application from day one.

### Developer speed

Future tickets can focus on actual product features instead of repeatedly setting up Next.js.

### Testing

The app has independent lint, typecheck, and build commands, which will later run in CI.

### Product clarity

Anyone browsing the repository can immediately see that the business/client product has its own application.

## 12. How will we validate it?

The ticket is expected to pass:

```text
pnpm --filter @serviq/client-console lint
pnpm --filter @serviq/client-console typecheck
pnpm --filter @serviq/client-console build
```

In plain English:

- **lint** checks for code-quality problems;
- **typecheck** checks whether TypeScript sees invalid data usage;
- **build** proves Next.js can turn the source code into a production-ready application bundle.

Manual QA also requires opening the app in a browser and confirming the foundation page renders without browser-console errors.

These checks must actually run successfully before this ticket is marked Done. We do not mark them as passed based only on how the files look.

## 13. Plain-English glossary

**Frontend:** The part of a product a user sees and interacts with in a browser.

**Application shell / scaffold:** The basic working structure of an app before real product features are added.

**Next.js:** The framework that organizes and builds the web application.

**React:** The library used to create reusable user-interface components.

**TypeScript:** JavaScript with additional type rules that catch many mistakes earlier.

**Tailwind CSS:** A styling system used to build the visual interface.

**Route:** A URL/page inside the application.

**Layout:** Shared structure that surrounds pages.

**Build:** Turning development source code into files ready for production deployment.

**Lint:** Automated code-quality checks.

**Console error:** An error reported by the browser's developer tools while the app is running.
