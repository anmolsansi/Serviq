## 1. What is the Customer Web application?

The **Customer Web** application is the part of Serviq that an end customer will eventually use when they need help.

Imagine a customer opens a company's support page and types:

```text
Where is my order?
```

or:

```text
An item is missing. Can I get a refund?
```

That conversation will eventually happen inside this application.

The Customer Web app is different from the Client Console. The Client Console is for employees of the business. Customer Web is for the business's customers.

OPE-254 creates the basic working shell for that customer-facing experience.

---

## 2. What are we actually building in this ticket?

We are **not** building the AI chat experience yet.

We are building the empty but functional web application that future chat features will live inside.

Think of opening a new store.

Before customers can shop, the store needs:

- a physical location;
- doors;
- electricity;
- a sign;
- a safe basic structure.

The shelves, products, checkout counter, and customer-service desk come later.

OPE-254 is creating that safe structure for the customer-facing Serviq experience.

---

## 3. Where does this app live?

The application is created at:

```text
apps/customer-web/
```

Its workspace package name is:

```text
@serviq/customer-web
```

This exact name matters because future build scripts and shared packages need a predictable way to refer to the app.

---

## 4. Why does Customer Web need to be separate from Client Console?

The two applications serve different audiences and different security levels.

### Customer Web

Used by external customers.

Future examples:

- send a message;
- receive an AI answer;
- see a delivery status;
- confirm a refund request;
- request a human support agent;
- give feedback.

### Client Console

Used by employees inside the company.

Future examples:

- manage AI settings;
- upload knowledge;
- inspect conversations;
- approve actions;
- manage support agents;
- view audit logs.

Keeping them separate makes the system easier to secure.

A customer should never accidentally receive internal administrative code or privileged business screens simply because both experiences were mixed together.

A useful analogy is a bank. Customers use the public banking app. Bank employees use a separate internal system. They may connect to the same backend, but they should not be the same application.

---

## 5. What technology does this app use?

The Customer Web shell uses the same frozen frontend foundation as the other Serviq web applications:

- **Next.js** for the application framework;
- **React** for reusable UI pieces;
- **TypeScript** for safer code;
- **Tailwind CSS** for styling;
- **ESLint** for automated code-quality checks.

Using the same basic technology across Serviq's web apps means engineers do not have to learn a completely different framework for every surface.

At the same time, each app remains a separate package so its code and security responsibilities stay clear.

---

## 6. What files did we add?

The scaffold contains the normal building blocks of a Next.js application.

### `package.json`

Describes this application and its dependencies.

It also defines commands such as:

```text
dev
build
lint
typecheck
```

This means Customer Web can be developed and validated independently.

---

### `tsconfig.json`

Turns on TypeScript rules.

We require strict TypeScript because this app will later process sensitive ideas such as:

- customer identity;
- order IDs;
- action confirmations;
- streamed AI responses;
- support handoff state.

Strong type checking helps catch mistakes such as treating a missing value as if it always exists.

---

### `next.config.ts`

Contains Next.js configuration.

It is intentionally minimal right now because unnecessary configuration creates unnecessary maintenance.

---

### ESLint configuration

Adds automated checks for common source-code mistakes.

This is one of the guardrails that future customer-facing code will have to pass.

---

### Tailwind/PostCSS configuration

Connects the styling system to the build process.

This gives future UI tickets a ready styling pipeline without deciding the final visual design in this scaffold ticket.

---

### `src/app/globals.css`

Contains only the minimal global styling necessary for the current shell.

We are avoiding fake design work that would later need to be deleted when the actual Serviq customer experience is implemented.

---

### `src/app/layout.tsx`

Provides the outer structure shared by the application's pages.

Later, this may become the place where customer-facing metadata and common app structure are applied.

---

### `src/app/page.tsx`

Displays a simple placeholder such as:

```text
Serviq Customer Support
Foundation scaffold
```

This is intentionally simple.

The goal is to prove the app renders successfully, not to pretend the chat product is already finished.

## 7. How will the finished customer experience eventually work?

The future flow may look like this:

```text
Customer opens support page
        ↓
Serviq identifies which company this page belongs to
        ↓
Customer starts or resumes a conversation
        ↓
Customer sends a message
        ↓
Backend decides whether to use knowledge, tools, or both
        ↓
AI response streams back to the browser
        ↓
Customer may see an action or confirmation request
        ↓
If needed, a human support agent joins
```

OPE-254 only creates the browser application at the top and bottom of that flow.

The intelligence and backend communication will be added in later tickets.

---

## 8. Why not add chat right now?

Because "chat" is not just a text box.

A production support conversation eventually needs to deal with:

- conversation IDs;
- customer identity;
- streaming responses;
- retries;
- network failures;
- citations;
- tool/action cards;
- confirmation states;
- human handoff;
- accessibility;
- mobile layout;
- duplicate-message prevention;
- error handling.

If all of that were hidden inside a scaffold ticket, it would be difficult to review and easy to get wrong.

We are therefore making the application shell first and adding each major behavior through dedicated tickets.

---

## 9. What did we intentionally NOT add?

This ticket does not include:

- chat messages;
- AI calls;
- API calls;
- customer authentication;
- tenant/company URL routing;
- Server-Sent Events or other streaming logic;
- file/image uploads;
- action-confirmation cards;
- support-agent handoff UI;
- analytics;
- shared design-system components;
- fake order or refund data.

Keeping those items out protects the scope of the ticket.

---

## 10. Why did we use small commits?

The application was assembled in small logical commits rather than one giant generated commit.

Conceptually, the history looks like:

```text
Define package
      ↓
Configure TypeScript
      ↓
Configure Next.js
      ↓
Add code-quality checks
      ↓
Connect Tailwind styling
      ↓
Add global styles
      ↓
Add app layout
      ↓
Add customer-facing placeholder page
```

This helps reviewers understand what each part does and makes it easier to undo one bad configuration without removing the whole app.

## 11. What does this improve?

### Clear product boundaries

Customer-facing code has a dedicated home.

### Security preparation

External customer code is separated from employee/admin code.

### Faster future development

Chat and identity tickets can focus on actual feature behavior instead of repeating app setup.

### Better testing

The app has its own lint, typecheck, and build commands.

### Consistency

It follows the same engineering standards as the other Serviq web applications.

### Mobile-first preparation

Because this is a standalone customer app, future UI work can optimize it for simple, responsive customer interactions without inheriting the dense layout needs of the internal Client Console.

## 12. How will we validate it?

The ticket expects these commands to succeed:

```text
pnpm --filter @serviq/customer-web lint
pnpm --filter @serviq/customer-web typecheck
pnpm --filter @serviq/customer-web build
```

The app also needs manual browser QA.

At minimum, we should confirm:

- the page loads;
- the expected Serviq Customer Support text appears;
- there are no browser-console errors;
- the basic page works at desktop width;
- the basic page works around 375px mobile width.

The ticket stays In Progress until those checks actually run successfully.

## 13. Plain-English glossary

**End customer:** The person contacting a business for help.

**Frontend:** The browser interface the user sees.

**Scaffold:** The minimum working structure of an application before real features are added.

**Next.js:** The framework used to organize and build the web app.

**React:** The library used to construct reusable interface pieces.

**TypeScript:** JavaScript with stronger type rules that catch many errors earlier.

**Tailwind CSS:** The styling system used by the frontend.

**Streaming:** Sending a response gradually as it becomes available instead of waiting for the entire response to finish first.

**Tenant:** One business/company using Serviq. Serviq is designed so one company's data remains separated from another company's data.

**Authentication:** Proving who a user is.

**Build:** Converting development code into production-ready web files.
