# OPE-254 — Detailed Implementation Record

**Ticket:** OPE-254 — V1.0.04 — Scaffold the customer-web Next.js application  
**GitHub issue:** #5  
**Branch:** `ope-254-customer-web-scaffold`  
**Status:** In Progress  
**Depends on:** OPE-252 root monorepo toolchain

## 1. Goal

Create the standalone frontend shell for Serviq's end-customer support experience without adding chat, authentication, tenant routing, streaming, or other product features yet.

This app is the customer-facing side of Serviq. It is intentionally separated from the workforce/client console because the two surfaces have different users, permissions, security boundaries, UI density, and deployment needs.

## 2. Application boundary

Created:

```text
apps/customer-web/
```

with package identity:

```text
@serviq/customer-web
```

**Why:** End customers must never share the same frontend trust boundary as tenant administrators or human support agents.

**What it improves:**

- reduces the risk of accidentally exposing workforce-only code or navigation to customers;
- makes customer authentication/session logic independently reviewable;
- allows the public support surface to be optimized for performance and accessibility separately;
- keeps future embedded/widget work aligned with one customer-specific reference implementation.

## 3. Frozen frontend stack

The scaffold uses:

- Next.js App Router;
- React;
- strict TypeScript;
- Tailwind CSS;
- source files under `src/`.

**Why:** Reusing the Serviq frontend baseline avoids multiple incompatible frontend architectures inside the same monorepo.

**What it improves:**

- consistent developer tooling;
- shared future packages for contracts/config/UI;
- predictable build behavior;
- easier cross-app upgrades and security patching.

## 4. App-local scripts

The application defines:

```text
dev
build
lint
typecheck
```

**Why:** Customer Web must be independently testable and buildable.

**What it improves:**

- CI can validate only the affected app;
- future customer-channel tickets get explicit acceptance commands;
- failures in another frontend do not prevent targeted development/debugging.

## 5. Strict TypeScript

Strict mode is retained and the handwritten scaffold does not intentionally add `any`.

**Why:** Future Customer Web code will handle customer identity, action confirmations, SSE event payloads, citations, escalation state, conversation state, and protected actions. Those are contract-heavy flows where loose typing can produce security and UX bugs.

**What it improves:**

- safer integration with shared/generated API contracts;
- better handling of customer-visible state transitions;
- fewer runtime errors around nullable conversation/action state.

## 6. Styling pipeline

A minimal Tailwind/PostCSS setup and base stylesheet were added without implementing the final customer chat design.

**Why:** The scaffold needs to prove the approved styling pipeline works while leaving actual UX implementation to dedicated design/feature tickets.

**What it improves:**

- prevents default framework demo styling from becoming product code;
- allows later Serviq design tokens/shared primitives to integrate cleanly;
- avoids coupling the foundation ticket to visual redesign work.

## 7. Root layout and metadata

A customer-specific root layout/metadata foundation was added.

**Why:** Customer Web should be clearly identifiable as the Serviq customer-support application from its first executable version.

**What it improves:**

- provides the future location for global customer providers/session boundaries;
- removes generic scaffold branding;
- keeps customer-facing metadata distinct from workforce/platform applications.

## 8. Minimal placeholder page

The root page shows a minimal `Serviq Customer Support` foundation message.

**Why:** OPE-254 is not the chat ticket. Adding fake messages, fake citations, or placeholder customer actions now would create misleading behavior and unnecessary cleanup later.

**What it improves:**

- keeps the ticket focused and reviewable;
- proves the route renders;
- preserves the exact feature scope for later tickets.

## 9. What was intentionally not added

OPE-254 excludes:

- tenant-slug routing;
- conversation creation;
- message composer;
- SSE streaming;
- customer identity verification;
- citations;
- action confirmation cards;
- human escalation UI;
- API calls;
- shared design-system work;
- client-console/platform-console logic.

These are future product slices, not scaffold responsibilities.

## 10. Why this separation matters for Serviq

The end-customer workflow is one of the two primary product workflows. Keeping it independent makes future architecture cleaner:

```text
Customer Browser
     |
     v
customer-web
     |
     v
Customer Conversation APIs
     |
     +--> Agent Runtime
     +--> Human Support state
     +--> Confirmation/Approval state
```

The customer browser never needs direct access to provider credentials, workforce roles, platform controls, or internal support-only metadata.

## 11. Micro-level commit strategy

The scaffold was pushed through small configuration/content commits rather than one generated blob. The branch separately introduces package configuration, TypeScript, framework configuration, linting, styling pipeline, global CSS, layout/metadata, and the final placeholder.

This improves reviewability because a reviewer can reason about each foundation concern independently.

## 12. Security impact

No customer authentication shortcut or fake identity is implemented. This is important: an unauthenticated placeholder is safer than pretending auth exists when it does not.

No API keys, provider secrets, workforce tokens, or private customer data are present in browser code.

The physical app separation also reduces the chance that future support-agent/admin bundles accidentally leak internal functionality to the public customer surface.

## 13. Downstream value

Future customer-experience tickets can now rely on:

```text
apps/customer-web/src/app
```

and can add, in controlled increments:

- `/support/[tenantSlug]` routing;
- conversation bootstrap;
- streamed AI/human messages;
- citations;
- confirmation cards;
- escalation/human-takeover states;
- feedback;
- responsive and accessibility behavior.

## 14. Validation status

Static scaffold review is complete. Runtime gates still need to run with pnpm/dependencies available:

```bash
pnpm --filter @serviq/customer-web lint
pnpm --filter @serviq/customer-web typecheck
pnpm --filter @serviq/customer-web build
```

Manual QA must also run the app and verify the placeholder renders at desktop and 375px widths without browser console errors.

The ticket remains In Progress until those checks pass.
