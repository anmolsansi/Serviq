## 1. What is the Platform Console?

Serviq is designed to support many different businesses.

Each business will have its own Client Console, customer conversations, settings, knowledge sources, AI configuration, and support workflows.

But Serviq itself also needs to be operated.

Someone on the Serviq team may need to answer questions such as:

- Is the platform healthy?
- Are AI providers responding normally?
- Are background jobs stuck?
- Is one company creating unusual traffic?
- Are queues becoming overloaded?
- Did a deployment cause failures?
- Is a feature flag enabled?
- Is a global rate limit too high or too low?
- Which tenant is affected by an incident?

The **Platform Console** is the future internal control room for the people operating Serviq itself.

OPE-255 creates the application shell for that control room.

---

## 2. A simple analogy: airport passenger app vs air-traffic control

Imagine an airport.

Passengers use one set of systems:

```text
Check flight
View gate
Get boarding pass
```

Airport operators use very different systems:

```text
Monitor runway activity
Inspect delays
Coordinate failures
Control operations
```

It would be unsafe and confusing to put air-traffic-control screens inside the passenger app.

Serviq follows the same idea.

The Customer Web app is for customers.
The Client Console is for employees of a business using Serviq.
The Platform Console is for trusted Serviq platform operators.

---

## 3. Why does this need its own application?

The Platform Console has the highest level of operational visibility in the product.

A normal business user should not be able to see another company's information or change platform-wide controls.

Future Platform Console capabilities may include:

- tenant lookup;
- service health;
- provider health;
- queue lag;
- failed background jobs;
- dead-letter work;
- incidents;
- global feature flags;
- global rate limits;
- security/abuse signals;
- platform usage;
- operational audit events.

Because these are privileged capabilities, we create a separate application and trust boundary from the beginning.

This makes it easier to apply stronger authentication, authorization, network controls, and audit rules later.

## 4. What did we build in this ticket?

We built only the **foundation shell** of the Platform Console.

The application lives at:

```text
apps/platform-console/
```

Its package name is:

```text
@serviq/platform-console
```

The current visible page is intentionally simple and identifies the application as the Serviq Platform Console foundation.

No real platform data is displayed yet.

## 5. What technology is used?

Like the other Serviq web applications, Platform Console uses:

### Next.js

Provides the web application framework, routing, build process, and server/web capabilities.

### React

Provides reusable components for the future interface.

Examples might eventually include:

```text
Service Health Card
Queue Status Table
Incident Timeline
Tenant Search Result
Provider Health Badge
```

### TypeScript

Adds stricter rules to JavaScript so many mistakes can be caught before the application runs.

Strict TypeScript is particularly valuable in privileged software because a mistaken assumption about an ID, status, permission, or configuration value can have a much larger effect than a normal visual bug.

### Tailwind CSS

Provides the styling pipeline for future interface work.

### ESLint

Checks source code for common quality problems.

---

## 6. What files did we add and why?

### `package.json`

Defines the Platform Console as its own workspace application.

It includes app-specific commands such as:

```text
dev
build
lint
typecheck
```

This allows platform-console code to be validated independently from customer-facing apps.

---

### `tsconfig.json`

Turns on the TypeScript configuration and strict type checking.

This gives future privileged features an early safety net against invalid assumptions.

---

### `next.config.ts`

Contains the Next.js configuration.

It is intentionally minimal because this ticket should not invent deployment or security features before those contracts are formally implemented.

---

### ESLint configuration

Adds automated source-code quality checks.

This becomes one of the gates future operator features must pass.

---

### Tailwind/PostCSS configuration

Connects the styling system to the app's build pipeline.

This prepares the app for later UI implementation without designing the full platform console in this scaffold ticket.

---

### `src/app/globals.css`

Contains only the basic global styles needed by the application shell.

---

### `src/app/layout.tsx`

Provides the shared outer layout and metadata for pages inside Platform Console.

Later pages such as `/health`, `/tenants`, or `/incidents` will live inside this application structure.

---

### `src/app/page.tsx`

Provides the initial visible page.

It currently acts as a simple proof that the Platform Console application can render.

No fake system-health data is shown.

Why avoid fake data?

Because a placeholder dashboard with made-up green health indicators can give readers the false impression that real monitoring has already been implemented.

We prefer an honest foundation page until the actual backend and observability integrations exist.

## 7. What will this application eventually do?

A future platform operator may use the app like this:

```text
Operator signs in
        ↓
Serviq verifies privileged operator identity
        ↓
Operator opens Platform Console
        ↓
Operator views system health
        ↓
One queue shows abnormal delay
        ↓
Operator opens queue/job details
        ↓
Operator identifies affected service or tenant
        ↓
Operator follows an incident workflow
        ↓
Any privileged action is permission-checked and audited
```

OPE-255 creates only the frontend shell required for those future flows.

---

## 8. Why are we not adding operator authentication now?

Authentication for the Platform Console is security-sensitive.

It should not be casually invented inside a scaffold ticket.

A future ticket must define things such as:

- who counts as a Serviq platform operator;
- how they sign in;
- whether stronger multi-factor authentication is required;
- which platform roles exist;
- which actions require extra approval;
- how operator actions are audited;
- how tenant access during incidents is limited.

Until those rules are implemented, this ticket deliberately avoids pretending authorization exists.

---

## 9. What did we intentionally NOT add?

OPE-255 does not include:

- platform-operator login;
- real tenant search;
- real system health;
- provider-health APIs;
- queue monitoring;
- job retry controls;
- feature flags;
- rate-limit editing;
- security-event data;
- incident management;
- cross-tenant data access;
- production infrastructure calls;
- backend APIs.

This protects the trust boundary by ensuring sensitive features are introduced only in tickets that explicitly define their security behavior.

## 10. Why use small commits?

The scaffold was built in separate logical steps instead of one large generated commit.

The process is conceptually:

```text
Create package definition
      ↓
Configure TypeScript
      ↓
Configure Next.js
      ↓
Configure linting
      ↓
Connect Tailwind styling
      ↓
Add global styles
      ↓
Add root layout
      ↓
Add minimal Platform Console page
```

This history helps future reviewers answer, "Why was this file introduced?" without studying one large mixed change.

---

## 11. What does this improve?

### Stronger security boundaries

Platform administration is physically separated from tenant/client and customer applications.

### Clear ownership

Future operational code has a defined home.

### Easier auditing

Later privileged behavior can be reviewed and monitored separately.

### Lower accidental exposure risk

There is less chance of accidentally shipping platform-only interface logic to a public customer application.

### Faster future development

Operational feature tickets can focus on actual health, queue, incident, or security functionality rather than app setup.

### Consistent engineering

The same Next.js/React/TypeScript foundation is used across all Serviq web applications, reducing unnecessary technology differences.

## 13. Plain-English glossary

**Platform operator:** A trusted person responsible for operating Serviq itself, not a normal customer or tenant employee.

**Trust boundary:** A separation between areas of a system that have different security privileges.

**Tenant:** One business/company using Serviq.

**Queue:** A waiting line of background work that workers process asynchronously.

**Queue lag:** How far behind the workers are in processing queued work.

**Dead-letter queue:** A place where work is sent when it repeatedly fails and needs investigation.

**Feature flag:** A switch that can turn a product/system behavior on or off without rewriting the entire feature.

**Rate limit:** A rule restricting how many requests can be made in a certain period.

**Incident:** An operational problem that needs investigation and resolution.

**Audit event:** A permanent or append-oriented record that says who did something, what they did, and when.

**Scaffold:** The minimum working application structure before real product features are added.
